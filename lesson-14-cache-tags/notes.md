# 📝 Нотатки Уроку 14

### Питання та відповіді з уроку:

**П: У тебе є інтернет-магазин. Юзер додав товар у кошик. Який метод краще використати, щоб оновити лічильник кошика в шапці сайту?**
**В:** Найкраще використати `revalidateTag("cart")`. 
- **Чому:** Кошик відображається на всіх сторінках (в шапці). Використовувати `revalidatePath` для всього сайту — занадто "дорого" для сервера. Тег дозволяє оновити тільки конкретну функцію лічильника кошика миттєво по всьому сайту.

**П: Чи можна викликати `revalidateTag` всередині звичайної сторінки або Server Component (не в Server Action чи Route Handler)?**
**В:** Технічно можна, але це **погана практика**. 
- **Ризик:** Це може призвести до нескінченного циклу перерендерінгу (Сторінка каже: "я стара" -> Next.js намагається її оновити -> вона знову каже: "я стара").
- **Закон:** Отримуємо дані (read) на сторінках, очищуємо кеш (write/invalidate) у Server Actions або API.

**П: Що станеться, якщо я викличу `revalidateTag("fake-tag")`, якого не існує?**
**В:** Нічого. Next.js просто проігнорує команду (fail-safe). Додаток не впаде, помилок у консолі не буде.

### Мої висновки:
- `revalidateTag` — це **очищення** кешу (видалення), а не його миттєве оновлення. Оновлення станеться автоматично при наступному запиті користувача (Lazy Loading).

**Профілі ревалідації в revalidateTag(tag, Profile):**
- **`'max'` (Stale-While-Revalidate)**: Пріоритет на продуктивність. Користувач отримує старі дані з кешу, а оновлення йде у фоні. Наступний запуск покаже нове.
- **`{ expire: 0 }`**: Пріоритет на свіжість. Кеш видаляється миттєво, користувач чекає на свіжі дані (блокуючий запит).
- **`updateTag(tag)`**: Спеціальна функція для Server Actions, яка є аналогом `{ expire: 0 }`. Зроблена для зручності, щоб не писати складні об'єкти конфігурації в екшенах.

**Чому в консолі багато логів рендерінгу?**
- **Паралельні маршрути (Slots)**: `@projects` та `page.tsx` рендеряться незалежно та одночасно.
- **Strict Mode (Dev)**: React подвоює виклики для пошуку помилок.
- **Cache Population**: Під час першого "прогріву" кешу Next.js може робити кілька проходів для збору метаданих та тегів.

**Кейс: Коли все ламається (ENOENT, build-manifest.json):**
- **Причина:** Найчастіше це синтаксична помилка (наприклад, зайва крапка), яка збиває компілятор з пантелику.
- **Рішення:** 
  1. Знайти і виправити помилку в коді.
  2. Видалити папку `.next` у проєкті.
  3. Перезапустити `npm run dev`.

**Кейс: Error Boundary (`error.tsx`) не зникає після оновлення даних:**
- **Причина:** Стан помилки в браузері є "липким". Навіть якщо дані на сервері вже правильні, Клієнтський компонент помилки не знає, що треба спробувати рендеринг знову.
- **Рішення:** Використовувати функцію **`reset()`**, яка передається в `error.tsx` пропсом. Кнопка оновлення має спочатку виконати Server Action (`updateTag`), а потім викликати `reset()`.
- **Важливо:** `reset()` діє тільки локально. Якщо кнопка знаходиться в батьківському компоненті або в іншому слоті, вона не зможе скинути Error Boundary сусіда без повного оновлення сторінки або спеціальних хаків з `key`.
- **Різниця:** `router.refresh()` змушує сервер перерендерити дані, але **не скидає** активовані Error Boundaries у браузері. Тільки `reset()` може "вимкнути" стан помилки в клієнтському дереві React.
- **Глобальне скидання:** Якщо кнопку потрібно винести за межі Error Boundary, найпростіший шлях змусити UI оновитися — це `window.location.reload()` або зміна `key` батьківського компонента.

---

### 🏆 Підсумок Уроку 14:
1. **Invalidation Cycle:** `cacheTag` (маркуємо) -> `updateTag` (даємо команду на видалення) -> `reset()` або `revalidatePath` (оживляємо UI).
2. **Дані vs Стан:** Очищення кешу на сервері не означає автоматичного зникнення помилок у браузері. Треба завжди синхронізувати стан Клієнта (`reset`) зі станом Сервера (`updateTag`).
3. **Next.js 16:** Вимагає профілі для `revalidateTag` (наприклад, `'max'`), але для екшенів краще використовувати простіший `updateTag`.
